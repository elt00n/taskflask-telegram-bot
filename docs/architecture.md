# Архитектура Telegram Task Bot

## 1. Цель проекта

Telegram-бот помогает пользователям личных и групповых чатов быстро создавать задачи,
события и дела, назначать участников, получать напоминания, фильтровать список и
экспортировать данные в календарь.

Главный принцип интерфейса: сложная модель внутри приложения, но быстрое создание
задачи для пользователя. Название — единственное обязательное поле. Остальные поля
получают разумные значения по умолчанию и при желании меняются позднее.

## 2. Основные пользовательские сценарии

Примеры быстрого создания:

```text
/task Купить молоко
/task завтра 10:00 Позвонить врачу
/task в пятницу 19:00 Ужин @anna
/task до 25 августа Подготовить презентацию важно
```

После создания бот сразу сохраняет задачу и показывает короткое подтверждение с
кнопками `Изменить`, `Завершить` и `Ещё`.

Расширенные поля открываются постепенно:

```text
Изменить: Название, Время, Участники, Важность
Ещё: Описание, Напоминания, Повторение, Календарь, История, Удалить
```

В групповом чате бот не воспринимает обычные сообщения как задачи. Создание
запускается командой `/task`, кнопкой или ответом на сообщение бота.

Детерминированные правила разбора быстрых команд описаны в
[`docs/commands.md`](commands.md). Парсер возвращает структурированные данные, а
Telegram transport отвечает за сопоставление usernames с ID участников чата.

## 3. Значения по умолчанию

| Поле | Значение |
|---|---|
| Название | Обязательное поле |
| Создатель | Автор команды |
| Участники | Только автор |
| Чат | Чат, в котором создана задача |
| Статус | Новая |
| Важность | Обычная |
| Описание | Пустое |
| Дедлайн | Не задан |
| Продолжительность события | 1 час |
| Повторение | Выключено |
| Напоминание | Персональная настройка пользователя |
| Часовой пояс | Из профиля пользователя |
| Видимость | Все участники текущего чата |

Если время не указано, задача попадает во «Входящие». Если указано одно время
начала события, конец по умолчанию наступает через час. Выражение `до пятницы`
считается дедлайном, а `в пятницу 18:00` — временем начала.

Пользователь может настроить свои значения по умолчанию: продолжительность,
напоминание, часовой пояс, важность и сортировку.

## 4. Модель данных

### User

Пользователь Telegram. Главный внешний идентификатор — `telegram_user_id`, потому
что username может измениться.

Основные поля: внутренний ID, Telegram ID, username, имя, часовой пояс, язык,
персональные настройки, даты создания и изменения.

В доменном Go-коде Telegram ID обёрнут в отдельный тип `UserID`. PostgreSQL позднее
может использовать дополнительный внутренний ключ, который останется деталью слоя
хранения.

### Chat

Личный или групповой чат Telegram. Содержит Telegram ID, название, тип чата и
настройки. Каждая задача принадлежит одному чату.

В доменном Go-коде Telegram ID чата представлен отдельным типом `ChatID`. Значение
может быть отрицательным для групп и супергрупп, но не может быть нулевым.

### ChatMember

Связь между известным приложению пользователем и чатом. Telegram не всегда отдаёт
боту полный список участников, поэтому база пополняется по мере взаимодействия
пользователей с ботом и получения доступных обновлений.

### Task

Задача, событие или напоминание.

Основные поля:

- внутренний ID;
- публичный UUID/ULID;
- чат и создатель;
- название и описание;
- тип, статус и важность;
- начало, конец и дедлайн;
- часовой пояс и признак события на весь день;
- даты создания, изменения и мягкого удаления.

Публичный ID не является защитой. Доступ всегда проверяется отдельно.

### TaskParticipant

Связь «многие ко многим» между задачами и назначенными пользователями. Она нужна не
для просмотра — просматривать задачи могут все участники чата, — а для определения,
к кому относится задача и кто имеет право её редактировать. Связь может содержать
роль: владелец, ответственный или редактор. Список задач не дублируется внутри
пользователя.

### Reminder

Персональное напоминание участника о задаче. Одна задача может иметь несколько
напоминаний, а разные участники могут выбрать разные параметры.

Основные поля: задача, получатель, тип, точное время, время начала относительно
дедлайна, интервал повторения, ближайший запуск, время остановки, статус и время
последней отправки.

Поддерживаемые режимы:

- одна отправка в заданный момент;
- несколько отдельных напоминаний;
- повтор через заданный интервал;
- повтор до дедлайна или до завершения задачи;
- перенос напоминания кнопкой «Напомнить позже».

### CalendarConnection и CalendarEvent

`CalendarConnection` хранит подключение пользователя к календарному провайдеру и
зашифрованные учётные данные. `CalendarEvent` связывает внутреннюю задачу с внешним
событием и хранит ID события и состояние синхронизации.

### TaskHistory

Журнал важных изменений: кто поменял название, срок, участников, статус или удалил
задачу. Он помогает разбирать ошибки в общих задачах.

## 5. Права доступа

- Любой участник чата может просматривать все задачи, созданные в этом чате.
- Создатель может редактировать задачу.
- Назначенный участник может редактировать задачу, если его роль это разрешает.
- Участник чата, который не является создателем или назначенным участником задачи,
  может её посмотреть, но не может изменить.
- По умолчанию удалить задачу может только создатель.
- Удаление сначала мягкое и может быть отменено.
- Проверка выполняется в сервисном слое при каждой операции, а не только в кнопках.

Мягко удалённая задача получает `DeletedAt`: обычные списки перестают её возвращать,
но репозиторий сохраняет запись для истории, диагностики и будущего восстановления.
Редактирование и обычный просмотр такой задачи запрещены.

Команда `/tasks @user2` показывает дела `user2` в текущем чате: созданные им или
назначенные ему. Она не раскрывает задачи пользователя из других групп или личных
чатов. В личной переписке с ботом для такого запроса потребуется сначала выбрать
общий чат.

## 6. Списки, сортировка и фильтры

Базовые представления:

- входящие без срока;
- сегодня;
- ближайшие;
- просроченные;
- созданные мной;
- назначенные мне;
- дела выбранного пользователя в текущем чате;
- завершённые;
- задачи конкретного чата.

Фильтры: статус, важность, дедлайн, чат, участник, автор, совместные задачи и теги.

Сортировка по умолчанию: просроченные, затем важность, ближайший дедлайн и дата
создания. Результаты выдаются страницами. В PostgreSQL создаются индексы по чату,
участнику, создателю, статусу, важности, дедлайну и ближайшему напоминанию.

## 7. Компоненты приложения

Проект строится как модульный монолит: один сервис с чётко разделёнными частями.
Это проще разрабатывать и разворачивать, чем микросервисы, и достаточно быстро для
первой и последующих версий.

```text
Telegram
   |
   v
Telegram handlers ---> Application services ---> Repositories ---> PostgreSQL
                              |                         ^
                              v                         |
                       Reminder worker ----------------+
                              |
                              v
                           Telegram

HTTP server ---> OAuth callbacks / ICS feeds / health checks
Calendar adapters ---> Google Calendar / ICS
```

- Обработчики Telegram переводят команды и кнопки во внутренние запросы.
- Сервисы содержат бизнес-правила и проверки доступа.
- Репозитории изолируют SQL и PostgreSQL.
- Фоновый worker отправляет наступившие напоминания.
- HTTP-сервер принимает webhook Telegram, OAuth callback и отдаёт ICS-календари.
- Календарные адаптеры скрывают различия Google Calendar и ICS.

На старте все компоненты могут работать в одном Go-процессе. Позже worker можно
запустить отдельно без изменения бизнес-логики.

`cmd/bot/main.go` только собирает и запускает приложение. `domain` описывает
сущности, `service` — правила, `repository` — хранение, `transport` — внешний мир,
а `worker` — фоновую работу. Каталог `internal` имеет специальное значение в Go:
пакеты из него нельзя импортировать из чужого проекта.

В рабочем приложении интерфейсы репозиториев выполняет реализация `postgres` на базе
пула соединений `pgx`. SQL-схема меняется версионируемыми миграциями, встроенными в
бинарный файл и автоматически применяемыми при запуске. Реализация `memory` остаётся
для быстрых тестов без внешней базы. Сервисный слой зависит только от интерфейсов,
поэтому Telegram-команды и бизнес-правила не содержат SQL.

На этапе локальной разработки Telegram transport получает updates через long
polling. Он регистрирует отправителей команд как известных участников чата в
PostgreSQL, но сопоставление usernames с Telegram ID пока держит в памяти. Следующий
этап перенесёт этот каталог в таблицы пользователей и чатов. Production сможет
перейти на webhook без изменения бизнес-сервисов.

## 9. Надёжность напоминаний

Worker периодически выбирает из PostgreSQL наступившие напоминания, блокирует их от
параллельной обработки, отправляет сообщение и вычисляет следующий запуск.

Нужно предусмотреть:

- хранение времени в UTC и отображение в часовом поясе пользователя;
- защиту от повторной отправки;
- повторные попытки при временной ошибке Telegram;
- пересчёт при изменении срока;
- остановку при завершении или удалении задачи;
- минимальный интервал, защищающий от спама;
- тихие часы пользователя;
- сохранение ошибки и возможность диагностики.

На первом этапе PostgreSQL достаточно и как базы, и как очереди напоминаний. Redis
или отдельный брокер сообщений добавляется только при подтверждённой необходимости.

## 10. Календарь

Первый этап — экспорт отдельного события и персональная подписка в формате ICS. Это
работает с Apple Calendar и может использоваться с Google Calendar без хранения
OAuth-токенов.

Второй этап — подключение Google Calendar через OAuth 2.0 и создание/обновление
событий через API. Полную двустороннюю синхронизацию и CalDAV лучше отложить до
стабильной версии базовых функций.

## 11. Дополнительные возможности

Полезные функции, которые согласуются с архитектурой:

- кнопка «Напомнить позже» на 10 минут, час, день или выбранный срок;
- тихие часы, когда уведомления переносятся на утро;
- ежедневная или еженедельная сводка задач;
- повторяющиеся задачи и события;
- теги, поиск и сохранённые фильтры;
- шаблоны частых задач;
- создание задачи ответом на сообщение с сохранением ссылки на оригинал;
- обсуждение задачи в теме Telegram-форума;
- комментарии и вложения;
- назначение ответственного отдельно от остальных участников;
- подтверждение участия и уведомление об изменениях;
- обнаружение конфликтующих событий;
- архив и отмена случайного удаления;
- экспорт пользовательских данных;
- резервные копии, журнал ошибок и служебные метрики.

Для удобства важнее всего сначала реализовать быстрый ввод, понятные списки,
напоминания и кнопку «Напомнить позже». Остальные возможности добавляются поэтапно,
не усложняя основной сценарий.

## 13. Технические решения

- Язык: Go.
- Основное хранилище: PostgreSQL.
- Архитектура: модульный монолит.
- Локальный запуск: Docker Compose.
- Разработка: Telegram long polling; production: webhook при наличии HTTPS.
- Идентификаторы: внутренний ID плюс публичный UUID/ULID.
- Время: UTC в базе плюс часовой пояс пользователя.
- Секреты: переменные окружения, никогда не Git.
- Репозиторий: отдельный GitHub-репозиторий пользователя.
